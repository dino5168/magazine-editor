## 2. 原因（page-flip 2.0.7 的假設）

page-flip 把頁面畫在翻頁區（我們的 `#book`）裡，翻頁區比書大時，它照比例算出書的位置並置中（`getRect().left / top`）。但有幾條路徑**假設書就在翻頁區的左上角**：

- **硬頁**（`showCover` 時的封面與最後一頁）：`HTMLPage.drawHard` 用 `top: 0`；往左翻的那一面用 `translate3d(0, 0, 0)`、`transform-origin: 頁寬 0` → 直式書左右有空位時，左頁畫到翻頁區最左邊（問題 2）；橫式書上下有空位時，整頁畫到翻頁區最上面（問題 3）。
- 硬頁翻動時，下面那一頁也用同樣的 `top: 0` 畫（問題 3 的「下面那頁也上移」）。
- `flipNext` / `flipPrev`（鍵盤、工具列按鈕）的起點是 y = 1、x = 10，也是翻頁區座標。

我們的 `viewer.css` 讓 `#book` 佔滿整個 `#stage`，所以只要視窗比例和書不同，就一定有空位。

**實測驗證**（在書裡注入 CSS，不改檔案）：把 `#book` 設成剛好是書的大小並置中後，直式封面翻到左邊時貼著書背（337～768 → 落在 219～768），橫式封面翻動時停在原位（117～691，只有 3D 透視造成的上下延伸），軟頁的翻動軌跡相對書頂不變。

## 3. 修改規劃（一步一步）

### 步驟 1：`#book` 剛好是書的大小（修問題 2、3）

不改 page-flip（vendor 檔維持原樣、SHA-256 測試照舊），只改我們的 `viewer.js` / `viewer.css`：

- `layoutBook()`：讀 `#stage` 的寬高，算出書要多大：
  - 雙頁：`s2 = min(翻頁區寬 ÷ (2 × 頁寬), 翻頁區高 ÷ 頁高)`，書寬 = 2 × 頁寬 × s2；
  - 單頁：書寬 = 頁寬 × s1（`s1 = min(寬 ÷ 頁寬, 高 ÷ 頁高)`）；
  - 用雙頁還是單頁：**書寬 2 × 頁寬 × s2 ≥ 600 px 才雙頁**。page-flip 自己是在「翻頁區寬 < 2 × `minWidth`（300）」時改單頁，翻頁區 = 書之後兩邊的判斷一定一致（推導見步驟 1 的實作紀錄）。
  - `#book` 設 `position: absolute` 與算出來的寬高、置中的 left / top。
- 在 `new St.PageFlip` **之前**先註冊 `resize` 處理：page-flip 自己也聽 `resize`，我們的要先跑，它才讀到新的大小。縮圖列、目錄面板打開時原本就送 `resize`，會一起走這條路。
- 縮放比例 `--s` 照舊用 `getBoundsRect().pageWidth ÷ 頁寬`。
- 驗證：兩本參考書（各自的 1536×864、1400×900、窄螢幕）錄翻頁過程：直式封面往左翻貼著書背、橫式封面不上移；之前的瀏覽器測試（步驟 2～3c、真實匯出比對）重跑。

**結果（2026-10-14，完成）**：只改 `viewer.js` / `viewer.css`（vendor 的 page-flip 不動）。
- `layoutBook()`（`#book` 改 `position: absolute`，寬高與 left / top 由它設）：雙頁 = `2 × 頁寬 × s2 ≥ 2 × 300 + 1`（多 1 px：page-flip 讀整數的 `offsetWidth`，剛好在門檻上時兩邊才不會不同）；寬高取整數。在 `new St.PageFlip` 之前註冊 `resize`。
- **實作時多發現一個**：`loadFromHTML` 會在 `#book` 寫上 `min-width: 300px`、`min-height: 300px`、`width: 100%`（`autoSize`）與 `max-width`，蓋掉 `layoutBook` 的大小（第一次載入時書照樣佔滿翻頁區，只有之後 resize 才對），而且書不能小於 300 px（矮的視窗書會超出）。改成載入後清掉這三個值、再 `layoutBook()` + `flip.update()`。
- 驗證（使用者的兩本書複製到 scratchpad、換上新的 viewer；桌面上的檔案沒動）：
  - 版面：直式、橫式各 5 種視窗（1536×864、1400×900、1000×300、700×900、420×800）書的框剛好包住頁面、在翻頁區正中、單頁 / 雙頁正確；第一次載入（沒有 resize）也正確。
  - 翻頁（每 60 ms 一格）：翻開封面、翻回封面、從最後一頁往回翻：**硬頁一直貼著書背（≤ 1 px，修正前直式差 200 px）**、**垂直中心不動（≤ 0.2 px，修正前橫式上跳約 150 px）**、下面那一頁不動（≤ 0.3 px）。直式 13 頁的最後一頁在 12–13 的右邊，不是硬頁單獨翻，改成檢查平放的頁不動。
  - 之前的測試：`flipbook_preview` 重產後步驟 2、3、3a、3b、3c 全過；真實匯出比對（7 頁）仍逐像素相同、位置 ≤ 0.027 pt；cargo flipbook 15 個通過。
  - 附註：連續跑好幾個瀏覽器測試時，前一個無頭 Edge 還沒完全結束會搶同一個除錯埠，測試要間隔幾秒。

### 步驟 2：滾輪翻頁（問題 1）

- 在**翻頁區**（`#stage`）上聽 `wheel`（不是整個視窗：縮圖列有自己的橫向捲動、目錄面板要捲動、放大檢視要捲動與 Ctrl+滾輪縮放，都不受影響）。
- 方向：見第 4 節 Q1（建議：往下 / 往右 = 下一頁）。
- **一次手勢只翻一頁**：滑鼠滾輪一格約 100，觸控板一次滑動會連續送幾十個小事件。做法：累積 delta 到門檻（約 60）才翻；翻頁動畫進行中（page-flip 的 state 不是 `read`）與翻完後的短暫冷卻期間忽略；停止捲動約 200 ms 後累積歸零。
- Ctrl + 滾輪不攔（瀏覽器縮放整頁）；放大檢視開著時不作用（它在最上層，事件本來就到不了翻頁區）。
- 驗證：滑鼠一格翻一頁、連續快速捲動不會一次翻好幾頁、觸控板式的連續小事件只翻一頁、反方向、到頭 / 到尾不動、Ctrl+滾輪不翻頁、縮圖列與面板裡的滾輪照舊。

**結果（2026-10-14，完成）**：只改 `viewer.js`。
- `#stage` 的 `wheel`（`passive: false`）：取絕對值大的那一軸，正的（往下 / 觸控板往左滑）= `flipNext`、負的 = `flipPrev`。累積到 60 px 才翻；翻過之後這次手勢用掉（`wheelUsed`），之後的事件（含觸控板慣性）忽略到停止捲動 200 ms；page-flip 的 state 不是 `read`（翻頁中）時也忽略。Ctrl / Meta + 滾輪不攔。`deltaMode` 是行時每行 40 px（實測時用 16 px，Firefox 一格 3 行 = 48 px 不到門檻，改成 40）、是頁時用翻頁區高度。
- 驗證（無頭 Edge）：7 頁 15 項（一格往下 / 往上、快速 6 格只翻一頁、觸控板式 75 個小事件（含慣性）只翻一頁、左右滑兩個方向、小於門檻不翻、停頓後的新手勢再翻、到尾不動、Ctrl+滾輪不翻、deltaMode 行、工具列 / 縮圖列上不翻、放大檢視開著不翻書）；60 頁：縮圖列上的滾輪照舊橫向捲動、書不翻；兩本參考書用滾輪翻開封面再翻回；步驟 1 的版面 / 硬頁測試與之前的步驟 2～3c 重跑全過；cargo flipbook 15 個通過。

## 5. 規劃檢核

| 風險 | 對策 |
|---|---|
| 自己算書的大小，和 page-flip 的單頁 / 雙頁判斷不一致（我們排雙頁、它改單頁，頁面會被擠成一半） | 用同一個門檻（書寬 ≥ 2 × `minWidth`），翻頁區 = 書之後兩邊算的是同一個寬度；窄螢幕與「矮寬」視窗（例如 1000×200）都要測 |
| 我們的 `resize` 晚於 page-flip 的處理 → 它用舊大小算 | 在建立 PageFlip 之前註冊（事件依註冊順序執行）；測試裡改視窗大小後檢查頁面位置 |
| 硬頁 3D 翻轉時上下會超出書（透視造成，翻封面時可能蓋到工具列一下） | page-flip 的效果，不是這次的問題；記錄為已知。若要避免可以讓封面也是軟頁（之後另議） |
| 滾輪翻頁讓觸控板使用者一次翻好幾頁 | 累積門檻 + 動畫中忽略 + 冷卻；用模擬的連續小事件測試 |
| 改 vendor 的 page-flip 修 bug | 不改：vendor 檔維持原樣（升級容易、SHA-256 測試不用動），只改我們自己的版面 |
