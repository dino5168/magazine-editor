# 繪圖（仿 draw.io 的多樣圖形）可行性評估

> 任務檔：`01-繪圖.md`（2026-10-15）。本文件只做評估與分步規劃，**還沒有改程式**。
> 結論先講：**可行**。現有架構已經有「圖形 = 外框 + geometry」與匯出端的「路徑」繪製，只要加一種「路徑 geometry」，就能用資料（不是程式）擴充出幾十種圖形。draw.io 的引擎本身**不建議**引入。

---

## 1. 需求理解

| 項目 | 理解 |
|---|---|
| 目前狀態 | 圖形只有 5 種（矩形、圓角矩形、圓形、三角形、星形），來自 `ShapeGeometry` 的 4 種 kind。「繪圖」面板（`draw`）是佔位卡片「自由繪圖將於後續版本提供」。 |
| 使用者要的 | 像 draw.io「一般」分類那樣多樣的圖形：六角形、平行四邊形、菱形、圓柱、雲、文件、對話框、箭頭、梯形、波浪、資料卡…（見 `DrawIO.png`）。 |
| 本次範圍 | 可行性評估 + 分步計畫 + 需要使用者決定的問題。 |

`DrawIO.png` 的圖形可以分成四類，難度不同：

| 類別 | 例子 | 需要什麼 |
|---|---|---|
| A. 填色外框圖形 | 六角形、平行四邊形、菱形、梯形、Chevron、雲、文件（波浪底）、卡片（缺角）、對話框、十字、箭頭（粗箭頭） | 一條封閉路徑，拉伸到外框 → **主要目標** |
| B. 外框 + 內部線條 | 圓柱（頂部弧線）、Process（左右兩條直線）、立方體、內部儲存（十字線）、便條紙（折角） | 填色路徑 + 只描邊的細節線 |
| C. 有「調整把手」的參數圖形 | 箭頭的頭部大小、梯形的斜度、對話框尾巴的位置、圓柱頂部高度 | 參數 + 畫布上的黃色菱形把手 |
| D. 線條與連接線 | 直線、虛線、雙向箭頭、曲線箭頭、會黏在圖形上的連接線 | **新的物件類型**（端點而不是外框），另一套選取 / 拖曳行為 |
| （不算圖形） | Text、Heading、List、人形 icon、表格 | 文字物件已有；icon 適合走素材庫的 SVG |

## 2. draw.io 是怎麼做的（和本專案對照）

| draw.io | 本專案目前 | 對照結論 |
|---|---|---|
| mxGraph 引擎（SVG / Canvas 渲染、連線、版面） | Konva 畫布 + Rust（Typst PDF / HTML 系列）匯出 | **不換引擎**：mxGraph（或 maxGraph）是一整套編輯器，和 Konva 的選取、Transformer、跨頁、匯出全部衝突；而且它不管 PDF / EPUB 的「所見即所得」。 |
| Stencil XML：路徑以外框的 w × h 為單位，畫時拉伸（`aspect="fixed"` 才等比例） | 多邊形 / 星形「頂點拉伸到外框」（`shape-geometry.ts`） | **同一個概念**，只要把「頂點」推廣成「路徑」。 |
| `background`（填色）+ `foreground`（描邊細節） | 一個 fill + 一個 stroke | B 類需要「只描邊的子路徑」。 |
| 程式寫的參數圖形（`Shapes.js` 的 `size`、`arcSize`、`dx`…） | 星形的 `innerRatio`、矩形的 `cornerRadius` | C 類 = 再多一些參數；先不做把手，只在屬性面板給數字。 |
| 匯入 SVG 成為圖形 | 素材庫的 SVG 是**圖片**（`ImageElement`），不能改色 | 可以之後另排（見 §7）。 |

draw.io 的程式與 stencil 是 **Apache-2.0**：可以參考它的圖形公式；若直接搬它的 stencil 資料要附 NOTICE。由於我們只挑二、三十個一般圖形，**建議自己寫路徑定義（參考 draw.io 的外觀）**，不搬整個圖庫。

## 3. 現況盤點：哪些輪子已經有了

這是評估最重要的發現——**匯出端早就會畫任意路徑**：

| 已有的東西 | 位置 | 可以重用的方式 |
|---|---|---|
| `PathSegment`（Move / Line / Cubic） | `src-tauri/src/export/render.rs` | 新圖形的路徑直接轉成它。 |
| PDF 畫路徑（`kind: "path"` → Typst `curve`） | `export/template.typ` 的 `draw` | 已用在「有邊框的矩形 / 橢圓」，新圖形同一條路。 |
| EPUB / 翻頁書畫路徑（`svg_path_data` → `<path d>`） | `export/html/markup.rs` | 同上。 |
| 圖形的外框、拉伸、旋轉、Transformer、`bakeTransform` | `canvas-elements.tsx`、`geometry.ts` | 新圖形還是「框型圖形」，**全部不用改**。 |
| 填色 / 邊框（含虛線、色票連結）/ 圖形內文字 | `ShapeElement` 的 `fill` / `stroke` / `label` | 新圖形自動擁有。 |
| 屬性面板、圖層 icon、MCP `add_shape` | `properties-panel.tsx`、`layers-panel.tsx`、`automation/` | 加一個 geometry 選項即可。 |
| SVG path 字串解析、弧線轉貝茲 | 第三方：`svgpath`（npm，MIT，無相依） | 圖形定義用 SVG path 字串寫最直覺；用它做 `abs()` / `unarc()` / `unshort()` 正規化成 M/L/C/Z。**不自己寫 parser**。 |
| Konva 畫路徑 | `Konva.Path`（收 SVG `data`） | 不用自己畫；但見 §5 的「拉伸」注意事項。 |

所以真正要新寫的只有：**一份圖形定義資料 + 把定義算成路徑的純函式 + 一個新的 geometry 種類 + 面板 UI**。

## 4. 建議的設計

### 4.1 文件模型：加一種 geometry，不加物件類型

依 CLAUDE.md「新增框型圖形 = 在 `ShapeGeometry` 加一個成員，不是新增 Element」：

```ts
| { readonly kind: "preset"; readonly preset: string; readonly params: readonly number[] }
```

- `preset`：圖形庫裡的 id（`"hexagon"`、`"cloud"`、`"cylinder"`…），**id 一旦發布不改名**（同紙張 preset 的規則）。
- `params`：該圖形的參數（例如梯形斜度 0–0.5、箭頭頭部比例）；沒有參數的圖形是空陣列。
- 現有 4 種 geometry **不動**（不需要升級舊檔），矩形 / 橢圓 / 多邊形 / 星形照舊有自己的屬性面板。

### 4.2 路徑由前端算，Rust 只畫（關鍵決定）

比照「換行由編輯器決定、Typst 只負責定位」與「頁碼 = 匯出時才變成圖形」：

1. 圖形定義與公式**只寫在 TypeScript**（`lib/editor/shape-presets.ts`）：`presetPath(preset, params, width, height) → PathCommand[]`（pt，已拉伸，只有 M / L / C / Z）。
2. `buildExportRequest` 在**匯出副本**上把 `preset` 換成一個只給匯出用的 `path` geometry（帶算好的路徑），Rust `render.rs` 把它轉成既有的 `PathSegment` 畫。
3. Rust 不知道每個圖形長什麼樣子，**不需要兩邊各寫一份公式**（目前多邊形 / 星形就是兩份，靠測試守著）。

Rust 端要做的：
- `format.rs`：`ShapeGeometry::Preset { preset, params }` 的驗證只檢查格式（id 字元、長度、params 個數與有限數值），**不認圖形名稱**；不認識的 preset 在畫布上畫成虛線外框（同「圖片遺失」的處理），匯出略過並回報。
- `ExportRequest`：接受匯出專用的 path geometry（或像 `textLayouts` 一樣另放 `shapePaths`，以 element id 為 key —— 計畫時二選一）。

### 4.3 路徑資料的形式

- **子路徑分角色**（對應 draw.io 的 background / foreground）：`fill`（封閉、填色 + 描邊）與 `detail`（只描邊，如圓柱頂部的弧、Process 的兩條直線、便條紙折角）。
- **拉伸方式**：座標以外框的比例（0–1）寫；需要「不跟著拉伸」的部分（圓角、箭頭頭部、圓柱頂部高度）由參數乘以 `min(w, h)`，用**公式**而不是固定 SVG，這是 draw.io `Shapes.js` 的做法，也是九宮格縮放的真正需求。
- **描邊粗細不能跟著拉伸**：要先把座標算成 pt 再畫（不能用 Konva 的 `scaleX/scaleY`），否則橫向拉長的圖形左右邊線會變粗。
- **虛線起點**：路徑起點決定虛線位置；畫布、PDF、EPUB 用同一串路徑，所以自然一致（同 `rounded_rect_path` 的經驗）。

### 4.4 畫布

- `ShapeBody` 加一個 case：`<Path data={...} />`（`Konva.Path`，資料來自 `presetPath`），`detail` 子路徑另一個 `fill` 為空的 `Path`。
- 命中判斷、Transformer、`bakeTransform`、跨頁複本、主頁內容、縮圖都經過 `ShapeBody` / `StaticShape`，不用另外改。

### 4.5 UI

- **「元素」面板**改成分類的圖形庫（基本 / 流程圖 / 箭頭 / 標註…），每個按鈕的圖示由**同一個 `presetPath` 產生 inline SVG**，不用另找 icon（新增圖形不必改 UI）。
- 底部工具列的圖形選單沿用「最近用過的圖形」，但清單改成常用的幾個 + 「更多…」打開面板。
- 屬性面板「樣式」分頁：preset 圖形顯示它的參數欄位（名稱、範圍來自定義），以及「換成另一個圖形」的下拉（保留填色、邊框、文字）。

## 5. 規劃檢核：可能出問題的地方

| # | 風險 | 影響 | 對策 |
|---|---|---|---|
| R1 | **填色規則**（nonzero / evenodd）：有洞的圖形（甜甜圈、框）三端不一致 | 洞被填滿 | 第一批只收沒有洞的圖形；之後要做時定義加 `fillRule`，Typst `curve(fill-rule:)`、SVG `fill-rule`、Konva `fillRule` 三端實測。 |
| R2 | 現有 Typst / SVG 路徑**一律最後 `close`**，不支援開放子路徑與多個子路徑 | `detail` 線條被硬接回起點 | `PathSegment` 加 `Close`，`template.typ` 與 `svg_path_data` 改成照資料決定是否封閉（會動到矩形 / 橢圓的現有輸出，要以 `export_preview` 疊圖確認沒變）。 |
| R3 | 圖形內文字的文字框一律是外框內縮 4 pt | 平行四邊形、圓柱、對話框的字可能壓到斜邊 / 尾巴 | 第一階段接受；之後定義可帶「文字區」（draw.io 也有 per-shape 的 label bounds）。 |
| R4 | 弧線（`A`）在三端行為不同 | 曲線位置差異 | 一律先由 `svgpath.unarc()` 轉成三次貝茲，三端只看到 C。 |
| R5 | 檔案格式升級（v14） | 舊版 App 開新檔 | 照慣例提升 `SCHEMA_VERSION`，舊版會明確說「檔案比較新」；舊檔不用升級。 |
| R6 | MCP 工具清單變大 | `add_shape` 的 enum 很長 | `add_shape` 收 `preset` 字串 + 新增 `list_shapes` 查詢工具。 |
| R7 | 選取 / 框選用的外框（`localBounds`）是外框，不是路徑 | 箭頭等細圖形框選時範圍較大 | 和目前多邊形相同，可接受。 |
| R8 | 參數的「黃色把手」要自己做 Konva 控制點（Transformer 沒有） | 工作量較大 | 放到後面的階段；先用屬性面板數字。 |

沒有發現「做不到」的地方；R2 是唯一會動到既有輸出的修改，放在早期並用疊圖驗證。

## 6. 分步規劃（一步一步，不一步到位）

每一步都可以單獨驗收、可以停下來。

| 步驟 | 內容 | 驗收 |
|---|---|---|
| 0 | **路徑管線補強**（不加新圖形）：Rust `PathSegment::Close`、多子路徑、開放子路徑；`template.typ` / `markup.rs` 跟著改 | `cargo test`；`export_preview` 疊圖，現有矩形 / 橢圓輸出不變 |
| 1 | **模型**：`ShapeGeometry` 加 `preset`（TS `types.ts`、`validation.ts`；Rust `format.rs` 驗證）、`SCHEMA_VERSION` 14、fixture 加一個 preset 圖形、`docs-website/types.html` | vitest + cargo test 讀同一份 fixture |
| 2 | **圖形庫核心**：`shape-presets.ts`（定義格式、`presetPath`、引入 `svgpath`），先放 3 個代表性圖形：六角形（純直線）、雲（曲線）、圓柱（填色 + detail） | 純函式測試（拉伸、描邊不變粗、路徑起點） |
| 3 | **畫布**：`ShapeBody` 的 preset case、`describeShape`、圖層 icon、遺失 preset 的畫法 | 瀏覽器實測（headless Edge）：建立、拉伸、旋轉、虛線邊框、圖形內文字 |
| 4 | **匯出**：`buildExportRequest` 把 preset 換成路徑、Rust 畫出 | `export_preview` / `epub_preview` 疊圖 ≤ 0.5 pt |
| 5 | **UI**：「元素」面板分類圖形庫（圖示由路徑產生）、底部工具列 | 人工操作 |
| 6 | **補齊圖形**：A、B 類約 25–30 個（依 §8 Q3 的清單） | 每個圖形一張疊圖 |
| 7 | **參數**：屬性面板的參數欄位、「換成另一個圖形」 | 測試 + 人工 |
| 8 | **MCP**：`add_shape` 收 preset、`list_shapes` | `mcp-tools.json` 快照、MCP 實測 |
| 之後另排 | 調整把手（C 類）、線條 / 箭頭物件（D 類）、連接線、SVG 轉圖形、自由繪圖、有洞的圖形 | 各自評估 |

步驟 0–4 做完，就證明整條路（畫布 → PDF → EPUB）通了；之後加圖形只是加資料。

## 7. 設計建議

1. **不要引入 draw.io / mxGraph / maxGraph**。它們解決的是「圖表編輯器」的問題（連線、自動版面），本專案是排版軟體，引擎衝突、而且破壞 PDF / EPUB 的所見即所得。借用的是它的**想法**（以外框為單位的參數化路徑）與**外觀**。
2. **圖形定義只寫一份（TS）**，Rust 只接收算好的路徑。這比目前多邊形 / 星形「兩邊各一份公式」更好維護，之後可以考慮讓多邊形 / 星形也走這條路（不急）。
3. **「線條 / 箭頭」不要硬塞成框型圖形**。線的兩端可以自由拖、粗細和箭頭樣式是線的屬性，應該是之後獨立的 `line` 物件類型（雜誌常用：分隔線、引線）。**連接線**（黏在圖形上）對雜誌排版價值低，建議不做。
4. **icon 類（人形、AWS 圖示…）走素材庫的 SVG**，不要變成圖形庫：它們是多色插圖，一個 `fill` 表達不了。
5. **「繪圖」面板的定位**要先決定（見 Q1）：圖形庫放「元素」面板比較自然（已經是「加入內容」類別），「繪圖」留給真正的自由繪圖 / 鋼筆工具。
6. 參考對象可以同時看 **PowerPoint / Affinity 的「預設形狀」**：它們和 draw.io 同樣是參數化路徑，而且更貼近雜誌排版（標註、橫幅、緞帶、對話框），清單選擇時可以混搭。
