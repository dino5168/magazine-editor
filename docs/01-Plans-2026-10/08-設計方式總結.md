# 設計方式探討：總結

> 對應：`08-設計方式探討.md`（2026-10-10 討論）。本次只做討論與決定方向，沒有改程式。

## 1. 「雙向建構」的方向

- **方向正確**：設計師由上而下定義規則（尺寸、網格、版式、樣式），編輯由下而上組裝內容，兩者共用同一套設計系統。InDesign、Affinity Publisher 都是這種結構，雜誌也適用。
- **要修正的理解**：四層圖裡的「排版引擎：把內容依規則轉成版面」在書籍系統（Typst / Pandoc / LaTeX）指的是**自動斷頁、自動流排**。本專案是 Canva / Affinity 式的**固定版面雜誌**，排版的是使用者，不是引擎。
- 因此本專案**不另建「排版引擎」子系統**。四層在本專案的對應：

| 圖上的層 | 在本專案的對應 | 現況（2026-10-10） |
|---|---|---|
| 設計系統（Top-down） | 紙張、邊界、主頁、格線、**樣式**、色票、範本 | 有紙張、邊界、主頁、方格格線（只用來吸附）；**沒有樣式**；色票是固定的 Tailwind 色 |
| 內容系統（Bottom-up） | 文章（story）、段落、圖片、表格 | 文字物件 = 一段純文字 + 一組樣式；素材庫有原始檔（圖片 / 文字 / 音訊） |
| 排版引擎 | 使用者擺放 + 文字框串接 / 溢排 + 量測換行 | 有量測換行（Konva 量測、匯出沿用，所見即所得）；沒有串接、溢排 |
| 輸出與預覽 | 畫布、PDF、EPUB | 畫布、PDF 完成；EPUB 依 `plan-epubv2` 重構中（階段 0 完成） |

## 2. 架構是否要調整

- **大方向不變**：文件模型 → 純 reducer → 畫布與匯出共用量測結果。
- **缺的是「規則」這一層的資料模型**：目前每個文字物件把字型、字級、顏色直接存在自己身上，沒有「引用某個樣式」的概念。需要補：
  - 文件層級的**樣式表與色票**，文字物件改為引用樣式 + 覆寫值（檔案格式升級，`types.ts` / `format.rs` / fixture / 匯出同步改）。
  - 主頁上的**欄格線 / 版心**（欄數、欄距），取代只能吸附的方格。
  - **範本** = 紙張 + 邊界 + 主頁 + 樣式表 + 色票的組合（即檔案系統第三階段的「系統素材庫與範本」）。

## 3. 決定：開發順序

1. **樣式系統**（段落 / 字元樣式、文件色票）。細節（分不分段落 / 字元、覆寫值怎麼存、UI）**實作時再討論**。
2. **欄格線 / 版心**（放在主頁，吸附也對齊欄）。
3. **範本**（新增文件時選擇；跨專案存放）。
4. **內容系統**：文字框內的富文字（多種樣式混排）→ 文字框串接與溢排 → 文章匯入（例如素材庫的 `.md` 自動套樣式）。

理由：

- 樣式是**檔案格式的變更**，越晚做，舊檔升級與要改的地方越多。
- 後面每一塊都引用它：範本沒有樣式只是複製檔案；富文字的每段要掛字元樣式；EPUB 的樣式可直接對應 CSS class；MCP 讓 AI 套「標題」樣式比逐一指定字型可靠。
- **不先做內容系統**：Konva 的 `Text` 一個節點只有一種樣式，富文字要自己逐段量測與繪製，匯出端（`render.rs`、`template.typ`、EPUB）也要跟著改，是整個專案技術風險最高的一塊；沒有樣式系統就先做，之後還要再遷移一次。

## 4. 素材管理

- 下一步（跨專案素材庫）和「範本」是同一件事，排在第 3 步一起規劃。
