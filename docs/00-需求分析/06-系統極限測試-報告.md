# 系統極限測試報告（200 頁）

需求：`06-系統極限測試.md`（依 `05-Story Test.md` 的版面產出 200 頁）。

## 結論

- **release build 輕鬆跑完 200 頁**：672 次 MCP 呼叫 7.9 秒全部成功，每次約 8 ms，從頭到尾不變慢；App 保留的物件數和成功的呼叫數完全一致（667 / 667）。WebView renderer 記憶體最高約 317 MB（開發版卡住時約 770 MB）。
- **前端邏輯不是瓶頸**：MCP 工具（`runTool`）加 reducer，200 頁時每次呼叫 0.03–0.08 ms，不隨頁數變慢（vitest 量測）。
- **瓶頸在 React 重畫**，兩個原因：
  1. **開發版限定**：React 19 開發版每重畫一個元件就呼叫一次 `performance.measure`（Performance 面板的元件軌道），這個呼叫在同一個視窗裡**越用越慢**（同樣 30 次呼叫，`measure` 從 1.8 秒變成 14 秒）。所以 `npm run tauri dev` 長時間大量編輯會一直變慢，原本的 200 頁測試在第 104 頁失去回應。production build 沒有這段檢測。
  2. **一般版也有**：「頁面」面板每次修改文件都把所有頁面方塊（每個帶一個 Radix 選單）重畫一次，成本和頁數成正比。已修正（見下方）。
- **MCP 回報成功不保證保留**：WebView 重新載入後，之前回報成功的修改可能不在（只剩最後一次自動備份的內容），呼叫端無從得知。

## 測試方式

- 腳本以 stdio 啟動 `magazine-mcp.exe`，走和 Claude Code 相同的 MCP 路徑。版型依 `05-Story Test` 的三種頁面循環（標題 + 兩欄文字 + 圖片佔位），每頁 3–4 個物件，共約 670 次呼叫。
- `add_page` 一次最多 100 頁（`ADD_PAGES_MAX`），200 頁分兩次。
- profile：設定 `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222` 後執行 `npm run tauri dev`，用 Chrome DevTools Protocol 的 `Profiler` 在 MCP 呼叫期間取樣，依函式彙整。

## 數據

### 第一次 200 頁（開發版，修正前）

| 進度 | 每次新增物件平均 |
|---|---|
| 第 1–20 頁 | 334 ms |
| 第 41–60 頁 | 616 ms |
| 第 81–100 頁 | 925 ms |
| 第 104 頁 | 30 秒沒有回應（「App 沒有在 30 秒內回應」），WebView 重新載入，之後的呼叫都失敗 |

頁面本身都建立了（`add_page` 很快），物件只保留到最後一次自動備份。

### 越用越慢（開發版，修正前，同一個視窗連續 7 輪，每輪 30 次呼叫）

| 輪 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| 平均（ms） | 154 | 177 | 242 | 309 | 366 | 425 | 557 |

這段期間 JS heap（約 160–190 MB）、DOM 節點數、canvas 數都持平，WebView 行程記憶體約 770 MB。

### 「頁面」面板修正前後（開發版，剛開啟的視窗，204 頁，30 次呼叫）

| | 修正前 | 修正後 |
|---|---|---|
| 每次呼叫平均 | 154 ms | 45 ms |
| CPU 取樣總時間 | 4,867 ms | 1,472 ms |
| `performance.measure` | 1,763 ms | 332 ms |

修正後 App 程式碼裡最多的是頁籤列 `EditorPageBar` 與 `PageMenu`，各約每次 2 ms，暫不處理。

### release build（含「頁面」面板修正，空白 A4 新文件 + 200 頁）

`npx tauri build --no-bundle`，橋接程式也用 release 版。

| 進度 | 每次呼叫平均（最近 20 頁） | WebView renderer |
|---|---|---|
| 第 20 頁 | 8 ms | 219 MB |
| 第 100 頁 | 7 ms | 286 MB |
| 第 200 頁 | 8 ms | 314 MB |

- 全部 672 次呼叫（`add_page` × 2、`add_text` × 400、`add_shape` × 267 等）0 失敗，總共 7.9 秒；`add_text` / `add_shape` p50 約 8 ms、最大 39 ms。
- 前 1/4 與後 1/4 的物件呼叫平均 7.9 / 8.3 ms：**不隨頁數變慢**。
- 核對：成功的新增 667 次 = 文件保留的物件 667 個，沒有頁面的物件數對不上。
- 跑完後 App 有回應，renderer 回收到 178 MB。
- 限制：release 版的遠端除錯參數沒有生效（9222 沒開），沒有量到畫面的重畫時間；呼叫是一個接一個送的，前一次的重畫若很慢會拖慢下一次，所以 8 ms 的節奏也表示重畫跟得上。

## 修正

`components/editor/panels/pages-panel.tsx`：`SheetTile` 改成 `memo`；每個方塊的 handler 改成一個共用、穩定的 `TileActions`（以 id 為參數）；選單內容改在方塊裡依 `kind`（`PageMenuItems` / `MasterMenuItems`）組出來。修改某一頁時，只有那一頁的方塊重畫。
