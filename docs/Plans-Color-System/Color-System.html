1. 結論先講

  • 方向對，但範圍要縮小。「具名顏色（色票）→ 樣式引用色票」這條主幹符合目前系統，而且 03-系統設計優先順序建議.md 已經把「文件色票」排在第一階段第 1 項。
  • PANTONE / ICC 這一層目前不適合做：主要輸出是 EPUB（螢幕、sRGB），畫布 Konva 只有 sRGB；PANTONE 色庫有授權問題；ICC 色彩管理牽動畫布、PDF、EPUB 三端。建議只在資料模型預留欄位，不實作。
  • 「全局設計 Token 引擎」不需要另外造：已經有一套可以照抄的機制——文字樣式（物件存實際值 + styleId，改樣式時 reducer 一次改寫所有引用）。色票照同一個模式做，畫布、量測、PDF / EPUB 匯出、Rust render 全都不用改。
  • 選單：放在「設定 → 文件 ▸ 色票...」（存進專案、可復原的文件設定，和頁面設定、頁碼管理同一組）。但日常套用要在調色板裡，選單只負責「管理」。
  • 改動幅度：中等，約等於當初「文字樣式」的一半到三分之二（檔案格式 v12、一組 reducer action、調色板多一區、一個對話框、MCP 工具），分 8 步做。

3. 評估「PANTONE / ICC → Token 引擎 → Color Tokens → Style」是否適合

層評估理由
PANTONE 專色庫暫不做
  • 授權：PANTONE 色值是商業授權資料（Adobe 2022 年起也要另外訂閱），不能直接內嵌進 public repo 的程式。
  • 輸出端：專色要 PDF 的 Separation 色彩空間；目前 PDF 由 Typst 產生，是否支援專色要實測（印象中只有 RGB / CMYK，未確認）。EPUB 是螢幕，專色沒有意義。
  • 專案方向：長期目標是 EPUB 固定版面為主、PDF 為衍生，且「已知限制」已寫明沒有 CMYK、出血、裁切線。
ICC 色彩管理暫不做Konva（Canvas 2D）只有 sRGB，無法做軟打樣（soft proof）；ICC 會同時牽動畫布、PDF（Output Intent、PDF/X）、EPUB 三端，是印刷流程的整包工作，應該和 CMYK、出血一起規劃，不是色票的一部分。
全局 Token 引擎不另造
  • 「引擎」做的事 = 名稱 → 值、改值時通知所有引用處。文字樣式已經有一套：物件存實際值 + 連結 id，改樣式時 reducer 一次改寫（restyleDocument）。照抄這套就是 token 引擎，不要再造一層。
  • 「全局」若指跨專案：素材庫、範本都還是每個專案各自一份，跨專案的「系統庫」排在第三階段（範本）。色票先做文件層級。
Color Tokens（色票）適合就是 03-系統設計優先順序建議.md 的「文件色票」：文件層級的具名顏色、可自訂、改色票時所有用到的地方一起變。
Style & Typography適合文字樣式已完成；樣式的文字顏色 / 陰影顏色連到色票即可。物件樣式是下一項，先有色票，物件樣式一開始就引用色票（不用之後再遷移）。

4. 建議的架構（縮小後的版本）

4.1 資料模型（草案，細節實作時再定）

// types.ts（草案）
interface Swatch {
  readonly id: string;
  readonly name: string;      // 文件內不重複，例如「品牌紅」
  readonly color: string;     // #rrggbb（不透明，見問題 Q3）
  // 預留，不實作：readonly cmyk?: [c, m, y, k]; readonly spot?: string;
}
interface EditorDocument { …; readonly swatches: Swatch[] }

// 引用處：照存實際 hex，另外記連到哪個色票（null = 沒連）
interface Stroke     { color; swatchId: string | null; … }
interface TextShadow { color; swatchId: string | null; … }
interface TextStyle  { fill;  fillSwatchId: string | null; … }
interface ShapeElement { fill; fillSwatchId: string | null; … }
interface Sheet      { background; backgroundSwatchId: string | null; … }
  • 為什麼照存實際值：和文字樣式同一個理由——畫布、measureTextLayout、Rust render、Typst 模板、EPUB 都不讀色票表，匯出端零改動；舊檔不需要升級成「只存引用」。
  • 透明度屬於使用處：色票是不透明的 #rrggbb；物件把它當成 50% 用時存 withAlpha(色票, 0.5) + swatchId。改色票時保留每個使用處自己的透明度（withAlpha(新色, colorAlpha(舊值))）。這等於 InDesign 的「色調 / 不透明度」，也讓頁面背景（不可透明）能共用同一組色票。
  • 斷開連結：在調色板選了不是色票的顏色 → swatchId: null。改透明度不斷開。

  • 放「文件 ▸」而不是「偏好設定 ▸」：色票存進專案、可復原、會標記未存檔，和頁面設定、頁碼管理同性質（SETTINGS_GROUPS 的分法正是「存在文件 / 存在這台電腦」）。
  • 只用 SETTINGS_PAGES 加一筆：選單項目、指令 settings.swatches、handler 都自動產生，對話框登記到 SETTINGS_DIALOGS（漏了會編譯失敗）。不用碰 MENUS。
  • 選單只負責管理，套用在調色板裡：每次改顏色都要開選單太慢。調色板最上面放「文件色票」一區，最後一個按鈕「管理色票...」開同一個對話框。
  • 「色票」工具面板（像「樣式」面板，點一下套用到選取）：建議先不做，等使用一陣子再決定；有了調色板那一區，面板只是多一個入口。
  • 快捷鍵：建議不設（「色票...」不是常用的管理動作）。

  1. Q1　範圍：這一輪只做「文件色票」（具名 sRGB 顏色），PANTONE / ICC / CMYK 只預留不實作——同意嗎？
    建議：同意。印刷色彩（CMYK、專色、ICC、出血）另開一個「印刷輸出」任務，和 PDF/X 一起評估。
  2. Q2　Tailwind 色票的地位：(a) 保留在調色板，當「原色庫」直接選（現在的行為）；(b) 只能用來「加入色票」，物件一律選文件色票。
    建議：(a)。(b) 太嚴格，排一頁草稿也要先建色票。
  3. Q3　色票能不能帶不透明度：10-12 的建議寫「可自訂 hex（含不透明度）」。本文件建議色票本身不透明，透明度留在使用處（理由見 4.1：頁面背景不可透明、改色票時保留各處透明度、和 InDesign 的色調概念一致）。要改成這樣嗎？
  4. Q4　自訂 hex 在哪裡輸入：(a) 只在「色票...」對話框（自訂色一定有名字）；(b) 調色板也可以直接輸入 hex（不具名）。
    建議：(a)。維持「畫面上的顏色都找得到出處」，也和 09-30「不保留自訂顏色」的精神接近。
  5. Q5　和文字樣式的覆寫：文字樣式的顏色連到「品牌紅」，某段文字顏色值一樣但沒連色票——算不算覆寫？
    建議：算（fillSwatchId 也是樣式欄位，比對自然包含）。否則改色票時那段文字不會跟著變，使用者會困惑。
  6. Q6　刪除還在使用中的色票：(a) 顏色保留、只取消連結（同文字樣式的刪除）；(b) 先問要換成哪個色票（InDesign 的做法）。
    建議：先做 (a)，確認框說明「N 處使用，顏色不變、取消連結」；(b) 之後需要再加。
  7. Q7　新文件的預設色票：空的，還是帶幾個（黑、白、內文灰）？舊檔開啟一律是空的。
    建議（2026-10-12 修訂）：帶三個——「文字」#171717（= 內建文字樣式與 DEFAULT_TEXT_FILL 的顏色）、「黑」#000000、「白」#ffffff；新文件的內建三個文字樣式連到「文字」，所以一開始改「文字」色票，所有標題 / 內文就一起變。頁面背景不預先連「白」（白紙是紙，不是設計色）。注意：tests/fixtures/default-text-styles.json 也是 Rust 升級舊檔時用的內建樣式，舊檔沒有色票，所以這份 fixture 的 fillSwatchId 要維持 null，連結只在 createBlankDocument 建立新文件時加上。
  8. Q8　對話框要不要即時預覽：改色票時畫布立刻變色。偏好設定的即時預覽機制只適用 App 偏好；文件要做預覽得另外做「草稿文件」。
    建議：第一版不做預覽（和頁碼管理一樣按確定才套用），色票列表本身顯示色塊就夠判斷。

9. 規劃檢核：發現的問題與風險

  1. 和既有決定衝突：progress.md 決定表與 CLAUDE.md 寫「顏色只能從 Tailwind v4 色票選、不保留自訂顏色」（2026-09-30）。10-12 已決定色票可以自訂，但要在實作計畫裡明確取代舊決定，並同步改 CLAUDE.md，否則之後的對話會被舊規則誤導。
  2. 透明度定義不一致：10-12 建議「色票含不透明度」，本文件建議「色票不透明」（Q3）。已決定：色票不透明，03-系統設計優先順序建議.md 的寫法要在實作計畫裡註明被取代。
  3. 內建文字樣式連到「文字」色票（Q7）：只在新文件加連結；default-text-styles.json（Rust 升級舊檔共用）維持不連結，否則舊檔升級後會引用不存在的色票、驗證失敗。
  4. 引用欄位分散在 5 種結構：Stroke、TextShadow、TextStyle、ShapeElement、Sheet。漏改一處 = 那裡的顏色不會跟著色票變。建議 swatches.ts 用一個「走過所有顏色欄位」的函式（同 mapStyledTexts）集中處理，測試用 fixture 覆蓋每一種。
  5. 偏好設定對話框共用調色板：「格線與參考線」用的是同一個 ColorPicker。如果文件色票區是「預設顯示」，參考線就能連到文件色票，但偏好不存在文件裡 → 換專案就失效。所以必須設計成呼叫端傳入才顯示（步驟 4）。
  6. 頁碼是虛擬圖形：pageNumberShape() 由規則算出圖形，規則裡的顏色連色票後，改色票要改寫的是 pageNumberRules，不是頁面上的物件。recolorDocument 要記得包含它。
  7. 主頁：主頁上的物件、主頁背景也是引用處；referenced 類的走訪要同時走 pages 與 masters（文字樣式已踩過這個點）。
  8. 變更範圍可能很大：改一個色票可能改寫上百個物件，但它仍是一個 action、一筆復原，reducer 只換有變化的物件（沒變的保留原參考），不會讓縮圖全部重畫。
  9. PANTONE 名稱：如果將來讓使用者自己輸入「PANTONE 186 C」當色票名稱，這只是名稱，不涉及授權；但不要內建 PANTONE 色值表。
  10. EPUB 重構（plan-epubv2）：色票之後可以變成 EPUB 的 CSS 變數，但這一輪匯出照舊輸出實際值，不依賴 EPUB 重構的時程。
