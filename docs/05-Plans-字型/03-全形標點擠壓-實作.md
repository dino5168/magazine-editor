# 03 全形標點擠壓三端一致 — 實作計畫

來源：`02-字型管理問題-實作.md` 步驟 7 的疊圖比對發現的既有問題（所有字型都有，內建黑體也是）。

## 0. 問題與決定

三端（畫布、EPUB / 翻頁書、PDF）對全形標點的寬度處理不同，所以有標點的行位置對不上：

| | 行中相鄰的標點（「：「」） | 行首 / 行尾的括號、引號 |
|---|---|---|
| 畫布（Chromium canvas：顯示與量換行） | 擠成半寬 | 不擠 |
| EPUB / 翻頁書（`html/css.rs`：`text-spacing-trim: space-all`） | 不擠 | 不擠 |
| PDF（Typst，`lang: zh, region: tw`） | 不擠 | **擠**（沒有開關） |

**決定（2026-10-29，使用者選定）：三端都不擠。** 理由：

- 匯出本來就不擠（只差 PDF 的行首 / 行尾），要改的主要是畫布。
- 任何閱讀器都一致：Firefox 不支援 `text-spacing-trim`，本來就不擠；如果改成「都擠」，EPUB 在 Firefox 和部分閱讀器還是會不同，PDF 也要在 Rust / Typst 模仿 Chromium 的擠壓規則（哪些標點配對、擠多少、每種字型的 `halt`），很脆弱。
- 代價：舊文件裡有相鄰全形標點的行，在畫布上會寬半個字，可能重新換行（匯出的 PDF / EPUB 不受影響，本來就不擠）。

## 1. 實測（2026-10-29，Edge 156，Noto Sans TC 100 px）

| 量法 | `：「` | `他說：「好。」然後走了` |
|---|---|---|
| canvas 不在頁面上（`createElement` 後沒放進 DOM）/ `OffscreenCanvas` | 150（擠） | 1050 |
| canvas 在頁面上，自己或上層的 CSS 是 `text-spacing-trim: space-all` | 200 | 1100 |
| DOM 預設（`normal`） | 150（擠） | 1050 |
| DOM `space-all` | 200 | 1100 |

- 內建的中文字型都沒有 `chws`，只有 `halt`（Geist 兩者都沒有）：Chromium 在沒有 `chws` 時用 `halt` 擠壓。
- canvas 2D 沒有控制擠壓的屬性（`ctx.fontKerning = "none"` 沒有影響），只吃 canvas 元素的 computed style，**所以必須在 DOM 裡**。
- Konva 量字（`measureTextLayout`、`node.measureSize`）用的是 Konva 自己建立、不在 DOM 的 dummy canvas：根元素設了 `space-all` 之後，主畫布量出 200，`measureTextLayout` 還是 150。
- 不在 DOM 的 canvas 裡，`trim-start` 這類值也沒有作用；在 DOM 的 `trim-start` 會把行首的「「」擠掉（`「引號` 300 → 250）。

## 2. 設計

### 2.1 畫布不擠（前端）

- `src/index.css`：在根元素（`html`）設 `text-spacing-trim: space-all`（這個屬性會繼承）。這樣畫布的 canvas、文字編輯框（contenteditable）、預覽都不擠，和 EPUB 相同；介面文字也一起不擠（看不出差別）。
- 量字的 canvas：Konva 的 dummy canvas 在第一次量字時由 `Konva.Util.createCanvasElement()` 建立。新增一個模組，在任何量字之前暫時包住 `createCanvasElement`，觸發一次量字，把建立出來的 canvas 放進一個隱藏、不佔版面的容器（`position: fixed`、`visibility: hidden`、尺寸 0）。容器在 DOM 裡，所以吃得到根元素的 `space-all`。包完立刻還原 `createCanvasElement`，其他 canvas（圖層、hit、cache）不受影響。
  - 自我檢查：設定完後量一次 `：「`，如果還是擠（例如 dummy canvas 已經先被建立），在 console 印警告。
  - 只在瀏覽器執行（vitest 是 node 環境，沒有 DOM）。
  - 依賴 Konva 10.5.0 內部（dummy canvas 由 `createCanvasElement` 建立、整個 App 共用一個）：**升級 Konva 時重測**，記進 `editor-text.md`。

### 2.2 PDF 的行首 / 行尾不擠（Typst）

- （步驟 2 實作時改了做法）Typst 0.15.1 的 `adjust_cj_at_line_boundaries`（`typst-layout` `inline/line.rs`）只在行的**第一個 / 最後一個項目是文字**時擠標點（`leading_text_mut` / `trailing_text_mut`）。所以 `template.typ` 的 `line-content` 在每行前後各放一個寬 0 的 `box`（`edge-guard`）：整行仍是同一段文字，不用挑哪些標點、kerning 也不變。原本想把行首 / 行尾的標點包進 `box`，但 box 裡的字自己成一行，一樣會被擠。
- `h(0pt)` 沒有用：長度 0 的間距會被丟掉，行首還是文字。
- 有字距 / 首尾置中（逐字分開、中間放 `h`）的行同樣處理。
- 依賴 Typst 內部：**升級 typst 時重跑 `full_width_punctuation_at_line_edges_keeps_its_width`**。

### 2.3 EPUB / 翻頁書

- 不用改。`html/css.rs` 的註解寫「canvas 量測時沒有壓縮」：現在已經不成立，改完後又成立了，註解要更新成「畫布也設 `space-all`（`index.css`）」。

## 4. 不做

- 「都擠」的排版（見 §0）。
- 直排、`trim-start` / `trim-both` 等選項：之後若要做成使用者可選的設定，三端都要各自實作，另開任務。
